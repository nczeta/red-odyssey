01 / PROJECT OVERVIEW

Making terrain
understandable.

A map shows where things are. A terrain explorer helps us ask what lies between them.

Red Odyssey is an educational WebGIS project for exploring a region of Mars through orbital imagery, topography and scientific context. Its goal is to bring visual interpretation and terrain-aware route exploration into a single, accessible interface.

Planetary imagery, elevation products and derived analyses often live in separate tools. The proposed atlas brings those perspectives together so learners can inspect a location, compare layers and understand how the landscape might influence a route.

Where the project stands

The OpenLayers frontend and layer adapters are implemented. The current map is an abstract local workspace. No planetary datasets, terrain measurements or Python routing service are connected yet.

04 / TERRAIN ANALYSIS

Reading the shape
of the surface.

A verified Digital Elevation Model will provide the foundation for the planned terrain analysis. Processing methods, units and uncertainty must be documented before measurements are exposed in the explorer.

Elevation & relief
Inspect surface height relative to the dataset’s documented vertical reference and evaluate elevation changes between locations.
Slope
Derive local gradients using the DEM’s actual horizontal spacing and vertical units. Coarse resolution can conceal small obstacles.
Morphology
Read landforms through elevation, illumination and contours. A hillshade is an interpretation aid, not a photograph.
Topographic difficulty
Combine selected terrain variables into a documented classification. Variables, thresholds and weights have not yet been defined.
Difficulty is not a safety certification.

A terrain classification cannot establish route safety, rover traversability or operational suitability. This educational project does not model every surface, vehicle or environmental constraint.

05 / ROUTE PLANNING

Between two points,
the terrain matters.

The intended workflow begins with a starting point and a destination. A Python service will use verified terrain products and a documented cost model to evaluate candidate paths. No definitive algorithm or cost function has been selected.

A

Define the question

Place endpoints in the configured map projection. Today, endpoint selection operates only in abstract local coordinates.

↳

Evaluate the terrain

The planned backend will evaluate terrain costs. Comparing alternative paths is a future possibility, not an implemented feature.

B

Interpret the result

The frontend is prepared to display route GeoJSON and explicitly supplied metrics. No route, distance or elevation profile is currently calculated.

Integration boundary: JavaScript request → FastAPI service → Python processing → route GeoJSON in a declared CRS.
